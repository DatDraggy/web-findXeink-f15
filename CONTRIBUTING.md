# Contributing

Thanks for looking. This is a small, deliberately boring codebase: plain ES modules, no build step,
no dependencies. If you can read JavaScript you can change every line of what ships.

## Run it

```
node serve.js        # or: npm run serve
```

Node 18+. It prints something like:

```
  OPEN THIS ON YOUR PHONE (same Wi-Fi):

     https://192.168.1.42:8443/          [WLAN]
```

Open that on your phone in **Chrome**. Chrome will warn *"Your connection is not private"* — expected,
the certificate was generated by your own PC a moment ago. Tap **Advanced → Proceed to … (unsafe)**.

**It has to be HTTPS.** `navigator.bluetooth` only exists in a secure context, so on a plain
`http://192.168.x.x` origin the API is not merely blocked, it is *undefined* — no error, no prompt,
nothing to debug. The certificate is generated on first run with the `openssl` that ships with Git
for Windows (or your system one), covers every LAN IP of the machine, and is regenerated
automatically when those addresses change. `http://localhost:8080/` also works, because localhost
*is* a secure context.

`serve.js` sends the same CSP and `Permissions-Policy` headers as the production hosts, so a header
mistake fails here rather than after deploying. `SECURITY_HEADERS=0 node serve.js` turns that off if
you need to rule it out. Ports: `HTTP_PORT`, `HTTPS_PORT`.

Web Bluetooth is Chromium-only. Chrome on Android works; Firefox, Samsung Internet and in-app
browsers do not implement it, and on iOS no browser does — an iPhone needs the third-party **Bluefy**
browser.

## Run the tests

```
npm test             # node test/run.js
```

No framework, no watcher, no config. `test/run.js` imports each `test/*.test.js` and calls its
default export:

```js
export default function run(t) {
  t.check('name', actual, expected);   // deep equality, prints a diff on failure
  t.ok('name', condition);
}
```

Add a file, add it to the list in `test/run.js`, done. Protocol and encoding changes need a test with
**literal expected bytes** — the values in there were captured from real hardware and from the vendor
app's own frame builder, and they are the only thing standing between a refactor and a display that
silently prints garbage.

## No dependencies. On purpose.

Zero, in `dependencies` and `devDependencies` alike, and there is no bundler, minifier or transpiler.

This is a page that can talk to hardware over Bluetooth and that reads images out of your photo
library. One compromised transitive package is enough to turn it into something else entirely, and a
build step would mean the code you audit is not the code that ships. So: if you need something, write
it. `js/qrcode.js` is a full QR encoder in one file for exactly this reason, and `tools/make-icons.js`
writes PNGs without an image library.

A pull request that adds a package will not be merged. A pull request that deletes code will get a
warm reception.

## Layout

```
index.html          the whole UI; every module is reached from here
css/app.css         all styling — CSP forbids inline <style> and style="..." attributes
js/main.js          wiring: element lookups, event handlers, app state
js/protocol.js      pure wire protocol — frames, CRC, obfuscation, manufacturer record, MODELS
js/device.js        Web Bluetooth transport: chooser, GATT, notifications, transfer state machine
js/image.js         pure pixel work: palettes, adjustments, dithering, quantisation, bit packing
js/crop.js          pure crop/fit geometry
js/render.js        turns a source (photo, text, QR, test pattern) into panel indices + preview
js/qrcode.js        QR encoder, ISO/IEC 18004 model 2
js/automation.js    pure program model for the slideshow runner
js/runner.js        drives an automation program against a real device
js/storage.js       IndexedDB persistence (the one module allowed to touch a browser store)
js/util.js          small shared helpers
sw.js               service worker: cache-first app shell, network as the fallback
serve.js            dev server (HTTPS + self-signed cert). Not part of the deployed site.
tools/make-icons.js regenerates icons/ — run it if you change the artwork
test/*.test.js      one per module
_headers            security headers for Cloudflare Pages / Netlify — the annotated original
vercel.json         the same headers for Vercel
.htaccess.sample    the same headers for Apache (rename to .htaccess to use it)
```

Only `main.js` and `render.js` may touch the DOM, and **no module may touch `document`, `window`,
`canvas` or `localStorage` at import time** — everything under `js/` has to import cleanly in Node so
the tests can reach it. A new module also belongs in `APP_SHELL` in `sw.js`; leaving it out is not
fatal (the worker caches it on the first online load) but it will not be there for a cold offline
start.

One CSP consequence worth knowing before it costs you an afternoon: `style-src 'self'` blocks
`style="…"` **attributes** just as much as `<style>` blocks, and it does it *silently* — the
attribute stays in the DOM, `getComputedStyle` just ignores it, and nothing is logged. Every
declaration belongs in `css/app.css`. Setting `element.style.foo` from JavaScript is CSSOM, not CSP,
and is unaffected. Likewise `script-src 'self'` means the one entry point is
`<script type="module" src="./js/main.js">`; no inline handlers, no inline scripts.

House style: 2-space indent, single quotes, semicolons, JSDoc on every export. Comment the *why*,
especially for firmware quirks; skip comments that restate the code.

## Adding a new panel or model

Panel geometry is **not** configured anywhere and should not become configurable. The device
broadcasts it, in the manufacturer record under company id `0x1A46`: byte 7 is the type (`>= 1` →
2 bpp 4-colour, `< 1` → 1 bpp), bytes 8–9 the width and 10–11 the height, both big-endian.
`decodeManufacturer()` in `js/protocol.js` reads it. A new panel of a known family therefore needs no
code at all — plug it in and it reports its own size.

What can differ is the **pixel scan order**, which the vendor app picks from the advertised device
name:

1. Add the exact advertised name to `MODELS` in `js/protocol.js`. Models 1, 2 and 3 (Air Wallet Pro,
   Wallet, F15) are plain row-major and are the default for any unknown name; model 4 (the F20) is
   the sole exception and is scanned **column-major from the right edge**.
2. If the new model needs an order that is neither of those, add a branch to `eachInDeviceOrder()` in
   `js/image.js`. That one function is the only place scan order exists.
3. Add a packing test with literal expected bytes. Useful anchors, all verified on hardware: a
   200×200 type-1 panel packs to exactly 10000 bytes with no per-row padding (one row is 50 bytes);
   all-white is `0xAA` per byte, all-black `0xFF`, all-red `0x00`, all-yellow `0x55`; a single black
   top-left pixel makes byte 0 `0xEA`.

Two things not to attempt. The firmware accepts **four** commands — `A1`/`A2` picture, `C1`/`C2`
card — and there is no clear-screen, battery read, time-set, sleep or OTA to be found; adding an
opcode does not add a feature. And **never write to characteristic `0xFFF5`**: its handler path can
soft-reset the device into a bootloader nobody has an image for.

## Releasing

* Bump `version` in `package.json`.
* **Bump `CACHE_VERSION` in `sw.js` in the same commit.** The worker is cache-first, so a client that
  already has the old files keeps serving them — changing index.html or a module and not bumping
  means the fix reaches nobody who has ever opened the app. Bumping changes `sw.js` itself, which is
  what makes the browser install a new worker, refill a fresh cache and bin the old one.
* **Four files carry the security headers and all four must say the same thing:** `_headers`
  (Cloudflare Pages, Netlify), `vercel.json`, `.htaccess.sample` (Apache) and `SECURITY_HEADERS` in
  `serve.js`. `_headers` is the source of truth and carries the reasoning in comments — change it
  there first, then mirror it into the other three. `serve.js` sends them in development precisely so
  a policy mistake surfaces before the deploy, which only works while it stays in step.
* Deploy is a file copy. There is nothing to build.

## Re-verifying the QR encoder

`js/qrcode.js` is the one module whose output cannot be judged by eye — a QR that looks right and
does not scan is worse than no QR at all. It was therefore verified against two independent
implementations, neither of which is a dependency of this project. If you touch the encoder, repeat
this outside the repo:

```
mkdir /tmp/qrcheck && cd /tmp/qrcheck
npm init -y && npm pkg set type=module && npm install qrcode jsqr
```

1. **Byte-for-byte, mask and version forced.** `QR.create(text, { errorCorrectionLevel, version,
   maskPattern })` against our `qrMatrix`. 36 of 44 payloads come out identical. The rest differ only
   because that library splits text into mixed-mode segments where we choose a single mode — a
   different but equally valid encoding, which the decode test below settles.
   Watch out: `BitMatrix.get` is `(row, col)`, **not** `(x, y)`. Reading it the wrong way round makes
   a perfectly good encoder look transposed.
2. **Decode the rendered pixels.** Run `qrToIndices` at real panel sizes, expand to RGBA, and feed it
   to `jsQR`. This is the test that matters, because it exercises the whole chain the display sees:
   mode selection, ECC, placement, masking, format info, quiet zone and integer scaling. It should
   round-trip 96/96 across four ECC levels, two geometries and twelve payloads including vCard and
   Wi-Fi strings.

`test/qrcode.test.js` then locks the result in as dependency-free golden matrices, so an accidental
change fails immediately without anyone having to install anything.

## Reporting a device that will not work

Include the advertised device name, the manufacturer record bytes under `0x1A46`, the GATT table, and
the frames in and out around the failure. The app's log view gives you all four.
