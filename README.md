# Web FindXeink F15

A browser app for FindXeink e-ink picture displays. Open it, pick your display, send a picture.
No install, no account, no server, no tracking.

It exists because the official app frequently cannot find these devices at all — a failure with a
[well-documented cause](#why-the-official-app-cannot-find-your-display) that turns out to be a bug in
the app, not in your hardware.

**[Open the app](https://findx.kieran.de/)** · Chrome on Android, Windows, macOS or Linux.
No install needed — it runs from the page.

[Source on GitHub](https://github.com/DatDraggy/web-findXeink-f15) · it is a static site, so you can
host your own copy or run it locally in one command.


---

## What it does

- **Send photos** with proper dithering to the panel's 4-colour palette (Floyd–Steinberg, Atkinson,
  ordered, or none), plus brightness, contrast, saturation and gamma.
- **Send text** — auto-sized to fill the panel, in any of the display's inks. Name badges, labels,
  signs.
- **Send QR codes** — a URL, a contact card, or Wi-Fi credentials. Generated at exact integer module
  scale so they actually scan.
- **Send a clock**, re-rendered at the moment of each send so an automation keeps it current.
- **Test patterns** for checking colour, alignment and pixel order.
- **A library** of saved pictures, stored in your browser.
- **Automation** — a block program that cycles pictures forever: picture, wait, go to start.
- **Works offline** once loaded, and installs as a home-screen app.

The panel's size and colour depth are read from the device itself. You should never need to know
them.

## Getting started

1. Open the app in **Chrome**. Firefox and Safari have no Web Bluetooth; on iOS you would need the
   third-party **Bluefy** browser.
2. **Turn Location Services on.** Android returns zero Bluetooth scan results with the system
   location toggle off — silently, with no error. This is the single most common reason a BLE app
   "cannot find" anything.
3. Press the button on your display to wake it, then tap **Find my display**.
4. Pick it in the browser's chooser. Everything else is automatic.

If it does not appear: un-pair the display in Android's Bluetooth settings if you ever paired it (a
bonded peripheral often stops advertising), and make sure the official app is force-stopped — these
displays accept exactly one connection at a time.

### Running it yourself

```
git clone https://github.com/DatDraggy/web-findXeink-f15.git
cd web-findXeink-f15
node serve.js
```

It prints a `https://192.168.x.x:8443/` address for your phone. Chrome will warn about the
certificate — it was generated by your own machine seconds earlier. Tap **Advanced → Proceed**.

The HTTPS is not optional: `navigator.bluetooth` does not exist on a plain `http://` LAN origin, so
the app cannot work there at all. (`http://localhost` is fine — browsers treat loopback as secure.)

```
npm test      # 851 assertions, no dependencies
```

### Deploying

It is a static site. Copy the directory to any host. `_headers` (Cloudflare Pages, Netlify),
`vercel.json` are included and set the same hardened policy. On a host that sets headers globally (or ignores per-directory config), apply the same policy at the server or CDN edge instead.

## Why the official app cannot find your display

The vendor's Android app was decompiled to work out the protocol. Two independent faults turned up
along the way, either of which alone stops it finding anything.

**1. Precise vs Approximate location.** The app targets Android 15 but declares `BLUETOOTH_SCAN`
without the `neverForLocation` flag, so Android still treats its scan as location-deriving and
delivers zero results unless *precise* location is granted. Its own permission check, however,
accepts `COARSE || FINE`. Tap **Approximate** on the permission dialog and the check passes, the scan
starts, the "Searching…" spinner animates — and the platform silently discards every result until the
60-second timeout. The app contains no "no device found" string, so there is never any feedback.

> Worth trying: Android Settings → Apps → FindXeink → Permissions → Location → **Precise**.

**2. A hard-coded allowlist in the scan callback.** Worth being precise, because it is not what it
looks like: the app never uses `ScanFilter` at all — `android.bluetooth.le.ScanFilter` appears
nowhere in the dex, and `startScan` is called with a null filter list. The filtering happens in
software, in `onScanResult`, and a result is dropped unless it clears two checks:

- `ScanResult.getDevice().getName() != null`. This is subtler than it sounds. The app never calls
  `ScanRecord.getDeviceName()`, so it is reading the Bluetooth stack's *cached* remote name rather
  than the name in the advertisement it just received — meaning a device that has never been bonded
  can be dropped on first sighting even while broadcasting its name perfectly.
- `ScanRecord.getServiceUuids()` must contain `0x1644`, a squatted, unassigned 16-bit UUID. Any
  firmware revision that changed or dropped it would break every install at once.

There is an escape hatch: a device whose MAC matches the last successfully connected one bypasses
the UUID check entirely, which is why the app works for some owners and never for others.

This app applies none of these gates.

## The protocol

Recovered from the vendor APK with jadx, then verified against real hardware — a FindXeink F15
accepted a full image and answered `F1 status 0 = success`, and this implementation's CRC validates
the device's own reply frames.

### GATT

| | |
| --- | --- |
| Service | `0000FFF0-0000-1000-8000-00805F9B34FB` |
| Write | `0000FFF3` — write **without response** |
| Notify | `0000FFF4` |
| CCCD | `0x2902` ← `01 00` |
| MTU | the vendor app requests exactly **247** and drops to 10-byte chunks if it does not get it |

The F15 also exposes `0000FFF5` labelled *"Verify"*, holding `EA 96 00…`. The vendor app never
touches it, and it is very likely an unprogrammed key slot on a code path that can soft-reset into a
bootloader. **Do not write to it.**

### Frame format

```
BC  op  seqHi seqLo  R0  R1  N   payload[N]   crcHi crcLo  AA
```

- `BC` phone → device; the device replies with `CC` and a `0x55` trailer instead of `0xAA`.
- `seq` is **big-endian**: `0xFFFF` for headers *and for the last data chunk*, otherwise the 1-based
  chunk number.
- `R0`/`R1` are random. **If `R0` is even the payload is XORed with `R1`**; odd means plaintext. The
  device accepts both and randomises its own replies between them. This app sends plaintext — it is
  far easier to read in a log, and since the CRC is computed *after* the XOR, a plaintext frame can
  be reproduced by hand.
- `CRC-16/CCITT-FALSE`, big-endian, over every preceding byte. Frames shorter than 11 bytes carry no
  CRC at all.
- Total frame length is always `N + 10`.

### Commands

The firmware accepts exactly four. There is no clear-screen, no battery read, no set-time, no sleep
and no OTA — every other feature in this app is done on our side.

| Opcode | Meaning | seq | Payload |
| --- | --- | --- | --- |
| `A1` | start picture | `FFFF` | `chunkSize, totalLen` (big-endian uint32) |
| `A2` | picture data | chunk number, `FFFF` on the last | ≤ chunkSize |
| `C1` | start card | `FFFF` | as `A1` |
| `C2` | card data | as `A2` | ≤ chunkSize |

Replies: `A1`/`C1` = READY (echoing the start payload back), `F1` = status, code in the first payload
byte — `0` success, `2` aborted, `5` low battery, `6` busy.

### The two screens

`A1`/`A2` write the main picture. `C1`/`C2` write a second stored image — the "contact screen" the
firmware swaps to when you **double-press** the device's single button. Both paths are confirmed on
hardware.

Worth knowing before you use it: the contact screen is **shown temporarily**. The panel renders it
immediately, then reverts to the main picture after a delay on its own. So it behaves like a peek,
not a mode you switch into — which is exactly right for a lost-and-found tag or a name badge you
show someone, and is why the app keeps the two destinations separate rather than treating the
contact screen as just another slot.

### Image format

| | 2 bpp (type ≥ 1) | 1 bpp (type < 1) |
| --- | --- | --- |
| Packing | 4 px/byte, MSB first | 8 px/byte, MSB first |
| Buffer | `(w × h + 3) / 4` | `(w × h + 7) / 8` |
| Values | `0` red · `1` yellow · `2` white · `3` black | `1` = black |
| Order | row-major, top to bottom | same |

There is **no per-row padding** — it is one flat pixel stream — and **no checksum** over the image.
The F20 is the sole exception to pixel order: it is scanned column-major from the right edge.

Handy for debugging: on a 4-colour panel, all-white packs to `0xAA` per byte, all-black `0xFF`,
all-red `0x00`, all-yellow `0x55`.

### Panel geometry

Not in the app, not in a GATT characteristic, not on the box. It is broadcast in the advertisement,
under manufacturer company ID **`0x1A46`**:

| Offset | Field |
| --- | --- |
| 0–6 | undecoded; most likely a marker plus the 6-byte MAC (iOS hides the MAC from apps, Android does not — which would explain why the Android app ignores these) |
| 7 | `type` — selects 1 bpp (`< 1`) or 2 bpp (`≥ 1`) |
| 8–9 | width, big-endian |
| 10–11 | height, big-endian |

Offsets are relative to the payload after the two company-ID bytes.

Note that `requestLEScan()` — passive advertisement scanning — **does not work on Android Chrome**
until `requestDevice()` has bootstrapped the Bluetooth permission, and reports the misleading
`NotFoundError: Bluetooth adapter not available` until then. This app therefore reads the
advertisement via `watchAdvertisements()` on the device you pick, which works reliably.

## Automation

Blocks run top to bottom; **Go to start** loops forever.

| Block | |
| --- | --- |
| **Picture** | show a specific library image |
| **Random** | show a random image, optionally never the same one twice running |
| **Wait** | at least 20 seconds |
| **Go to start** | loop back to the first block |

The 20-second minimum is a hardware limit, not a preference: the panel physically takes that long to
redraw. The runner enforces it independently of the program, so a corrupt saved file cannot hammer
the display.

**Web Bluetooth only lives while the page is open.** If you switch apps or the screen sleeps, the
browser throttles the tab and the slideshow pauses. Two design consequences:

- Every wait is stored as an **absolute due time**, never a countdown, so a throttled tab does not
  drift.
- On waking, the runner **skips** missed steps rather than replaying them. Catching up on an hour of
  backlog would mean watching the frame flicker through twelve refreshes.

Tick **Keep the screen awake** for an unattended display. It needs no permission prompt — only a
visible page.

## Permissions

Deliberately minimal. The app asks for exactly one thing.

| | |
| --- | --- |
| **Bluetooth** | Only when you tap *Find my display*, and only for the single device you pick in the browser's own chooser. The page never sees any other device. |
| **Screen wake lock** | Only while an automation runs, and only if you tick the box. No prompt. |
| **Storage** | IndexedDB, in your browser. No prompt, never uploaded. |
| **Network** | The app makes no requests at all after it loads. `connect-src` is pinned to `'self'`, so nothing can reach a third party. |

No account, no analytics, no cookies, no third-party anything. The shipped `Permissions-Policy`
denies geolocation, camera, microphone, payment, USB, serial, HID, MIDI and every sensor.

Your pictures live only in this browser. **Clearing site data deletes them** — use *Export
everything* in the Library tab to keep a backup.

The pure modules import cleanly in Node, which is why they can be tested without a browser or a
device. No dependencies, deliberately — see `CONTRIBUTING.md`.

## Compatibility

Confirmed working on a **FindXeink F15** (200 × 200, 4-colour). The protocol and the model table
also cover the **F20**, **FindXeink Wallet** and **Air Wallet Pro**, but those are untested — if you
have one, a report from the Advanced tab would be welcome.

### Is my tag one of these?

**This hardware is white-labelled**, so the name on the box is often not "FindXeink" at all — the
same tag sells on Amazon and AliExpress under other brands (LUCYLANKER is one). Brand is a poor
guide; the wire protocol is the real test.

You almost certainly have a compatible device if any of these hold:

- The seller told you to install the **FindXeink** app (`com.findn.findxeink`, or Lenze's
  `com.lenze.lenzefindxeink`).
- It has **exactly one button**, short-press turns it on, and **double-clicking shows a second
  "contact" screen**.
- The Advanced tab, once connected, shows service `0xFFF0` with characteristics labelled
  **`WRITE`**, **`NOTIFY`** and **`Verify`**.

The manufacturer of record is **Find future Technology (Shenzhen) Co., Ltd** — FCC grantee code
`2BH5G`, and the F15 itself is FCC ID `2BH5G-1FIND30` (granted August 2024, Part 15C, 2402–2480 MHz,
Bluetooth only — there is no Wi-Fi in it). Their only other filing, `2BH5G-AIRWALLET`, is the
Air Wallet Pro, which is why that model appears in the pixel-order table. The apps are published by
a different company, **ShenZhen Lenze Technology Co., Ltd**.

Neither the advertised manufacturer ID `0x1A46` nor the service UUID `0x1644` is a real Bluetooth
SIG assignment — both are squatted values — so they identify the product family but no company.

The BLE chip is unidentified: the FCC internal photos are too low-resolution to read the part.

### Browsers

Web Bluetooth is Chromium-only: Chrome and Edge on Android, Windows, macOS and Linux. Not Firefox,
not Safari, not in-app browsers. iOS has no Web Bluetooth in any browser; **Bluefy** ships its own
engine and works.
